# DUM BARBERSHOP Platform — Project Constitution

版本：1.0.0  
狀態：Frozen Core  
Owner：GitHub user `z72124223`

本文件定義專案不可被一般實作任務擅自改寫的最高規則。

---

## Article 1 — Git 是唯一最高標準

1. 本 Repository 是本專案規格、決策、程式、任務與歷史的唯一正式來源。
2. 未提交到 Git 的聊天內容、語音、截圖、臨時指令與本機改動，不具正式效力。
3. 若不同來源衝突，優先順序如下：
   1. `docs/PROJECT-CONSTITUTION.md`
   2. `docs/DECISIONS.md`
   3. `docs/BLUEPRINT.md`
   4. `docs/ARCHITECTURE.md`
   5. `docs/ROADMAP.md`
   6. 已核准的 GitHub Issue / Pull Request
   7. 其他文件與聊天內容
4. 任何正式決策都必須留下 Commit 或 Pull Request 紀錄。

## Article 2 — Owner 保留最終決策權

1. Owner 對品牌、營運、責任、個資、付款、會員與顧客權益擁有最終決策權。
2. AI、GPT Work、Codex、開發者或第三方工具不得自行替 Owner 做涉及責任或商業政策的決定。
3. 未決事項必須標記為 `Reserved` 或 `Needs Owner Decision`。
4. 緊急技術修正可以先採最保守、可逆且不影響客人權益的作法，但必須建立 Issue 說明。

## Article 3 — 專案核心產品範圍

本專案是 DUM BARBERSHOP 的：

- 深色品牌官方網站
- 單店、多人設計師工作室預約平台
- 客戶與服務歷史管理基礎
- 員工行程與操作介面
- iPhone 優先的管理體驗
- Apple Watch 行程與快捷操作延伸
- 未來會員、儲值、訂金、LINE 與分店擴充基礎

目前為單一門市，但資料與架構必須避免阻斷未來多門市能力。

## Article 4 — 多人工作室是寫死的核心

1. 系統從第一天即視為多人工作室，不得以單人預約模型作為核心資料結構。
2. 客人可以指定設計師。
3. 每位設計師必須能有獨立服務、排班、休假、封鎖時段與可預約時間。
4. 預約必須關聯到服務、設計師、時間、客戶與狀態。
5. 第一版可以只有一間門市，但不得把「只有一位設計師」寫死在資料庫、型別或商業邏輯。

## Article 5 — Git 管協作，本機做引擎

1. GitHub 管理規格、Issue、分支、Commit、PR、審核與版本。
2. 網站引擎、預約核心、整合與測試必須能在本機環境實作及重現。
3. 禁止只有某個聊天視窗、遠端沙盒或不可取得環境才能運作的核心程式。
4. 所有程式碼與必要設定說明必須回到 Repository。
5. 秘密、Token、付款金鑰、Google 憑證與真實客戶資料不得進入 Git。

## Article 6 — 預約與日曆責任分離

1. Google Calendar 目前是店內手動預約工具，並將作為重要整合目標。
2. 正式系統完成後，預約核心或其資料庫應成為預約狀態與客戶紀錄的主要來源。
3. Google Calendar 主要負責同步、顯示、提醒與封鎖忙碌時段，不應單獨承擔完整客戶資料、訂金、會員及狀態流程。
4. 第三方預約 App 尚未正式選定，不得把核心商業邏輯永久綁死單一供應商。

## Article 7 — 顧客進入門檻

1. 一般客人不需要登入即可預約。
2. 未來會員可以登入並與本店會員身分綁定。
3. 會員系統目前尚未定案，第一階段只能預留介面、資料欄位與 Adapter。
4. 未登入與會員登入都必須能共用同一份客戶主檔，避免重複與資料分裂。

## Article 8 — 訂金的保守原則

1. 第一版不強制所有客人支付訂金。
2. 系統必須預留可選訂金與訂金優先機制。
3. 在 Owner 尚未核准完整政策前，訂金客不得自動擠掉、取消或改動已確認的免訂金預約。
4. 訂金優先可先適用於等候名單、未確認請求與新釋出空檔。
5. 金額、退款、逾時、遲到、爽約及改期政策全部保留 Owner 決策。

## Article 9 — 個資與安全

1. 系統採最少必要資料原則。
2. 員工只能看到執行工作所需資料。
3. Apple Watch 預設不顯示過多敏感個資。
4. 真實客戶資料不得出現在測試、截圖、Issue、PR、Demo 或公開紀錄。
5. 所有外部整合都必須有權限、撤銷、錯誤與稽核設計。

## Article 10 — 可替換、可逆、可演進

1. 外部預約、日曆、通知、付款、登入與會員系統一律透過 Adapter 邊界整合。
2. 不得為了快速 Demo 把第三方 SDK 散落整個程式。
3. 初期採模組化單體或 Monorepo，先確保邊界清楚，再評估是否拆分服務。
4. 所有重大架構決策需記錄於 `docs/DECISIONS.md` 或 ADR。

## Article 11 — 變更本憲法的程序

本文件屬 Frozen Core。修改必須同時具備：

1. Owner 明確同意
2. 專用 GitHub Issue
3. 說明變更原因、影響與遷移方式
4. 獨立 Pull Request
5. PR 合併後更新版本號

一般功能 PR 不得順便修改本文件。
